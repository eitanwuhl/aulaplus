## 1. Executive Summary

### UI causes

- **Equivalent response options** appear in a **separate box** because a dedicated React component (`ResponseOptions.tsx`) renders them inside a `Card` below the item prompt. The box is always shown when `item.responseOptions?.enabled` and options exist; there is no code path that inlines these options into the question text/layout.
- **Evaluation map “Ítems” column** is the **count of items per section** (`section.items.length`). It is produced directly in `MapTable.tsx` from the normalized evaluation’s `sections`; the column is not a separate data structure but a derived value from the same sections that render the evaluation body.
- **Rubric** in V2 is **not generated by the Edge Function**. It is **derived in the frontend** from `evaluationSpec.meta.criteriosLogro` via pattern matching in `V2RubricPanel` (V2InfoPanels.tsx). There is no “rubric per question” in the current data model; the UI shows one global rubric per evaluation.

### Data-shape causes

- **equivalentResponseOptions** are sent by the backend (V2 spec) in two possible shapes: **object** `{ enabled, options, metacognitionText }` or **array** `[{ id?, format?, description? }]`. The normalizer (`v2Normalizer.ts`) converts both to a single `responseOptions` shape used by the renderer. The “separate box” is a **UI layout choice** (EvalItem → ResponseOptions as a sibling block), not a consequence of a different data source.
- **V2 evaluation spec is not persisted** on save. When the user saves after generating with V2, `evaluacion_generada` stores only the V1-shaped bundle (with empty HTML strings for V2 mode) and `evaluaciones` from that bundle. The detail page (`EvaluacionDetalle`) **always** uses `EvaluacionVisualRenderer` (HTML); it has no access to the V2 spec, so reopening a “V2” evaluation after save shows broken or placeholder content unless the bundle was later filled by another path.
- **Print/PDF** is implemented in two places: (1) **EvaluationRendererV2** uses `html2canvas` + `jsPDF` and a `.pdf-export-mode` class on the same React tree; (2) **EvaluationContentWrapper** uses `html2pdf.js` on a ref to the content div. There is no separate “print-friendly HTML” pipeline; the same DOM is captured for PDF. Global print styles live in `src/index.css` (`@media print`, `.pdf-export-mode`, `.pdf-no-break`).

## 2. Task A: Equivalent Response Options — UI Rendering Path

### A.1 Components that render equivalent response options

| Location | Component | Prop/field | How displayed | Data shape expected |
|----------|-----------|------------|----------------|----------------------|
| `src/components/evaluaciones/v2/EvalItem.tsx` | `EvalItem` | `item.responseOptions` (normalized) | Conditionally renders `ResponseOptions` in a wrapper `<div className="ml-10">` **below** the type-specific content (e.g. essay, paragraph). | `responseOptions: { enabled: boolean, options: Array<{ id, format, description }>, metacognitionText?: string }` |
| `src/components/evaluaciones/v2/ResponseOptions.tsx` | `ResponseOptions` | `options: NonNullable<NormalizedItem['responseOptions']>` | **Separate box:** a `Card` with `border-dashed border-primary/30 bg-primary/5`, title “Opciones de respuesta equivalentes”, subtitle “Elegí el formato que mejor se adapte a tu forma de aprender”, then a grid of options (Badge “Opción A/B/C” + format + description), and optional `metacognitionText` in an amber callout. | Same as above; expects `options.enabled`, `options.options` array. |

No other component in the evaluation UI renders “equivalent response options” or “opciones de respuesta equivalentes” by name. The only render path is: **EvaluationRendererV2 → EvalSection → EvalItem → ResponseOptions**.

### A.2 Source of the “separate box”

- **Not** from a V2-to-HTML converter: V2 is rendered with React components only; there is no conversion step that produces HTML for this block.
- **Not** from EvaluationRendererV2 directly: EvaluationRendererV2 renders sections and delegates to EvalSection/EvalItem; it does not render response options itself.
- **From** the **EvalItem** component (lines 57–61): it explicitly renders “Equivalent response options” in a **sibling block** below the item content, inside a `<div className="ml-10">` that wraps `ResponseOptions`. The “separate box” is the **Card** in `ResponseOptions.tsx` (lines 23–70).

So the separate box is a **direct result of the current component structure**: one block for the prompt + type-specific content, then a second block for response options. There is no conditional “inline vs box” path; it is always a box.

### A.3 Data flow and normalizer

- **Backend (modify-evaluation-v2):** Returns `evaluationSpec.sections[].items[].equivalentResponseOptions` in either:
  - **Object format:** `{ enabled: boolean, options: Array<{ id?, format?, description? }>, metacognitionText?: string }`
  - **Array format:** `[{ id?, format?, description? }, ...]` (documented in v2Types as `EquivalentResponseOptionsArray`).
- **Normalizer:** `src/services/evaluations/v2Normalizer.ts` (lines 305–394). For each item, if `item.equivalentResponseOptions` exists:
  - If object: reads `ero.enabled`, `ero.options`, `ero.metacognitionText` and normalizes each option to `{ id, format, description }`.
  - If array: maps array to same shape, infers `format` from description when missing.
  - Sets `normalized.responseOptions = { enabled: true, options: normalizedOptions, metacognitionText }` when at least one valid option exists.
- **Types:** `src/services/evaluations/v2Types.ts`: `EvaluationItemV2.equivalentResponseOptions` (lines 119–125); `EquivalentResponseOptions` and `EquivalentResponseOptionsArray` (lines 37–51). Normalized view: `NormalizedItem.responseOptions` (used by EvalItem/ResponseOptions).

**Minimal data shape** for the UI to show the box: after normalization, `item.responseOptions` must be `{ enabled: true, options: non-empty array }`. The box is shown whenever `item.responseOptions?.enabled && item.responseOptions.options && item.responseOptions.options.length > 0` (EvalItem.tsx lines 59–61).

## 3. Task B: Evaluation Map UI and “Items” Column Source

### B.1 UI component(s) that render “Mapa de la evaluación”

- **Single component:** `src/components/evaluaciones/v2/MapTable.tsx`.
- **Usage:** Rendered inside `EvaluationRendererV2.tsx` (around line 591): “Map of the test - PDF no break” comment, then `<MapTable evaluation={evaluation} />`. The `evaluation` prop is the **NormalizedEvaluation** produced by `normalizeV2Response(v2Response)`.

So the map is **only** used in the V2 render path (group evaluations screen when beta V2 is on and `v2RawResponse` is set). The V1/HTML path (EvaluacionVisualRenderer) does not include MapTable.

### B.2 Component hierarchy

- `EvaluacionesGrupo.tsx` (when `useBetaV2 && v2RawResponse`) → `EvaluationRendererV2` (v2Response) → `normalizeV2Response(v2Response)` → `NormalizedEvaluation` → `MapTable({ evaluation })`.
- `MapTable` receives `evaluation: NormalizedEvaluation` with `sections`, `totalPoints`, `totalItems`, `totalDuration` (from v2Types.ts NormalizedEvaluation).

### B.3 What “items” means and which field produces the column

- **“Items”** in the map UI is the **number of items (questions) per section**.
- **Column source:** The table header is “Ítems” (MapTable.tsx lines 46–50). The cell value for each section is `section.items.length` (line 74). The totals row shows `totalItems` (line 91), which comes from the normalized evaluation (sum of items across sections).
- **Data input:** In-memory only. The normalized evaluation is built from `v2Response.evaluationSpec` by `normalizeV2Response` in v2Normalizer.ts. Sections come from `spec.sections`; each `NormalizedSection` has an `items` array (normalized items). So the “items” column is **derived from the same section structure** that drives the evaluation body (EvalSection → EvalItem). There is no separate “items” entity in V1 or V2; it is `sections[].items.length`.

### B.4 How the map is used

- **Navigation/editing:** The map is **display-only**. There are no links, clicks, or edit actions that target the map. It summarizes sections, ítems count, points, and estimated time. Editing happens in the adjustment panel (EvaluationAdjustmentsPanel) or via regeneration, not via the map.

## 4. Task C: Rubric Generation and Rendering Audit

### C.1 Where rubrics are currently generated

- **Edge Function (modify-evaluation-v2):** **No rubric generation.** A search for “rubric” / “rúbrica” / “rubrica” in `supabase/functions/modify-evaluation-v2` returns no matches. The V2 spec does not include a rubric object.
- **Frontend:** Rubric **is not generated** as a stored artifact; it is **derived at render time** from **criterios de logro**.
  - **V2 path:** `src/components/evaluaciones/v2/V2InfoPanels.tsx` exports `V2RubricPanel`. It receives `criteriosLogro: string[]` from `evaluationSpec?.meta?.criteriosLogro`. If `criteriosLogro` is empty, it shows “No se generó una rúbrica para esta evaluación. La rúbrica se deriva de los criterios de logro ANEP seleccionados.” When present, it calls `deriveRubricLevels(criterio)` (lines 714–752) which uses **pattern matching** on the criterion text (e.g. “contrasta”, “argumenta”, “indaga”) to return four levels: `excelente`, `bueno`, `necesitaMejorar`, `insuficiente`. So the rubric is **fully derived from criterios**, not from a rubric field in the spec.
  - **V1 path:** `EvaluacionVisualRenderer` uses `SimplifiedSmartRubric` (and related components like `EnhancedSmartRubric`, `RubricaIntegrada`), which also derive levels from criterios ANEP (e.g. `derivarNivelesDesdeCriterioANEP` in SimplifiedSmartRubric.tsx). So V1 also has no AI-generated rubric; it is criterio-based derivation.

There is **no** “rubric per question” in the codebase. Rubrics are **global** (one set of criteria/levels per evaluation or per criterio).

### C.2 Data structure for rubrics

- **V1 HTML bundle:** No dedicated rubric structure in the HTML. The V1 flow stores HTML content in `evaluacion_generada.evaluation_bundle.versions.*`; rubric is not part of that bundle.
- **V2 EvaluationSpecV2:** `EvaluationSpecV2` (v2Types.ts) has `meta: EvaluationMetaV2`, which includes `criteriosLogro?: string[]`. There is **no** `rubric` or `rubricPerItem` field in the spec. So in V2, “rubric” exists only as **UI derivation** from `meta.criteriosLogro`.
- **DB storage:** Table `evaluaciones` has a column `rubrica jsonb` (migration `20251222000000_add_evaluaciones_explicit_save.sql`). The save flow in `EvaluacionesGrupo.tsx` (insert/update evaluacion) **does not** set `rubrica`; it sets `evaluacion_generada`, `ai_design_report`, etc. So the column exists but is **not populated** in the current save path. No other code was found that writes to `evaluaciones.rubrica`.

### C.3 UI that renders and allows editing the rubric

- **V2:** `V2RubricPanel` (inside V2InfoPanels) **renders** the derived rubric (collapsible panel “Rúbrica de evaluación”). It does **not** allow editing; it is read-only from criterios.
- **V1:** `SimplifiedSmartRubric`, `EnhancedSmartRubric`, `RubricaIntegrada` render rubrics; `EnhancedSmartRubric` has an “Editar rúbrica” action (line 487). Editing and persistence for that flow were not traced in this investigation; the important point is that the **V2** rubric is display-only and derived.

### C.4 Constraints for “rubric per question”

- The current data model has **no** per-item rubric in V2 (no `item.rubric` or `section.rubric`).
- Rubric is **global** and tied to `meta.criteriosLogro`. A “rubric per question” would require either: (1) extending the V2 spec (e.g. `item.rubric` or similar) and generating it in the Edge Function or frontend, or (2) deriving it in the frontend from existing item fields (e.g. prompt + criterio), which does not exist today.

## 5. Task D: Print/PDF Friendliness Pipeline

### D.1 Existing “print” or “export PDF” pathway

- **Path 1 — V2 (group screen):** In `EvaluationRendererV2.tsx`, a “Descargar PDF” button (lines 564–576) calls `handleExportPdf` (lines 338–468). Implementation: **html2canvas** on `contentRef.current`, then **jsPDF** to produce a multi-page PDF (A4, 10 mm margins). On failure, it falls back to `window.print()`. The same React tree (header, MapTable, sections) is used; a class `pdf-export-mode` is applied to the container during capture to apply PDF-specific CSS.
- **Path 2 — V1 / wrapper:** In `EvaluationContentWrapper.tsx`, “Descargar PDF” (lines 346–360) calls `exportToPdf`, which uses **html2pdf.js** (dynamically imported) to capture a ref (`contentRef`) and save as PDF. So there are **two** PDF export implementations: one in EvaluationRendererV2 (V2 content), one in EvaluationContentWrapper (used when versions are HTML and `useBetaV2` is false or no v2Response).
- **Browser print:** `window.print()` is used as fallback in EvaluationRendererV2. Global `@media print` rules in `src/index.css` (lines 597–631) hide nav/header/footer/buttons and set `@page { size: A4 portrait; margin: 15mm }`. No dedicated “Print” route or server-side PDF generation was found.

### D.2 Print-friendly HTML generation

- There is **no** separate “print-friendly HTML” pipeline. The **same** DOM that is shown on screen is used for PDF (and for print): either the React-rendered V2 tree or the HTML from `evaluation_bundle.versions.*` rendered inside the app. There is no conversion from V2 spec to a separate HTML document for print; the V2 path captures the React output.

### D.3 File paths and styling

- **PDF export logic:**  
  - `src/components/evaluaciones/v2/EvaluationRendererV2.tsx`: `handleExportPdf`, `contentRef`, `.pdf-export-mode` toggling.  
  - `src/components/evaluaciones/EvaluationContentWrapper.tsx`: `exportToPdf`, `contentRef`, `evaluation-export-content`.
- **Styling:** `src/index.css` (lines 455–631):
  - **.pdf-export-mode** (lines 469–493): Fixed width 718px (A4-friendly), block layout, white background, no shadows; typography and spacing adjustments.
  - **.pdf-no-break**, **.pdf-break-before**, **.pdf-break-after**: Page-break control.
  - **.pdf-export-mode** overrides for tables, cards, badges, buttons (hide buttons in PDF).
  - **@media print** (597–631): Hide nav/buttons, `@page` size and margin, `.print-content`, break-inside rules for cards/tables/rows.

So: **HTML is the same as the on-screen DOM.** Styling for print/PDF lives in `src/index.css` under the classes and `@media print` above.

## 6. Task E: Canonical Evaluation Representation in Practice

From actual code usage:

- **De-facto canonical format** is **hybrid and screen-dependent:**
  - On the **group evaluations screen**, when **V2 is used** (`useBetaV2 && v2RawResponse`): the **primary source of display** is the **V2 JSON spec** in memory (`v2RawResponse`). The UI renders via `EvaluationRendererV2` from normalized spec; `evaluationBundle.versions` is set to empty strings and is not used for content.
  - On the **group evaluations screen**, when **V1 is used**: the primary source is **V1 HTML** in `evaluationBundle.versions.A/B/C` (and legacy baseHtml/versionBHtml/versionCHtml). Display is `EvaluacionVisualRenderer` with `evaluation.content` = HTML string.
  - On the **evaluation detail page** (`EvaluacionDetalle`): **only** the V1 path exists. It reads `evaluacion_generada.evaluaciones` and optionally `evaluacion_generada.evaluation_bundle`. It **always** uses `EvaluacionVisualRenderer` with `evalItem.content` (HTML). There is **no** loading or rendering of V2 spec on the detail page; `v2RawResponse` is not persisted.

### Truth table

| Screen / flow | Representation used for display | What is saved to DB (evaluacion_generada) | Primary display source |
|---------------|----------------------------------|-------------------------------------------|------------------------|
| Group — generate V1 | V1 HTML | `evaluaciones` (cards with HTML content), `evaluation_bundle` (versions A/B/C as HTML strings), `ai_report`, etc. | `evaluationBundle.versions.*` → displayEvaluations → content |
| Group — generate V2 | V2 JSON (in memory) | Same shape as V1 save: `evaluaciones` (from displayEvaluations; in V2 mode these are built from empty bundle so content is error placeholder), `evaluation_bundle` (A/B/C empty), `ai_report`, etc. **V2 spec is not saved.** | `v2RawResponse.evaluationSpec` (in memory only) → EvaluationRendererV2 |
| Group — after save (V2) | N/A (user navigates away or refreshes) | — | — |
| Detail — open any saved evaluation | V1 HTML only | — (read-only load) | `evaluacion_generada.evaluaciones[].content` (HTML) via EvaluacionVisualRenderer |
| Detail — PDF | Not used on detail | — | Detail page does not use EvaluationContentWrapper; no PDF button on EvaluacionDetalle in the code paths seen. |

So: **saved state is always V1-shaped** (evaluaciones + evaluation_bundle). The **V2 spec is never persisted**; reopening a “V2” evaluation from the detail page therefore does not show the V2 content.

## 7. Implementation Constraints Discovered

1. **Equivalent options always in a box:** The only render path is EvalItem → ResponseOptions as a sibling Card; there is no component or prop to inline options into the question text/layout.
2. **Map “Ítems” column:** Trivial to remove or hide: it is a single column in MapTable.tsx (`section.items.length`); no shared “items” data structure to refactor.
3. **Rubric not generated by AI:** V2 Edge Function does not output rubric. Rubric is frontend-derived from `meta.criteriosLogro` with hardcoded pattern rules. No rubric-per-question structure in spec or DB.
4. **Rubric column unused on save:** `evaluaciones.rubrica` exists but is not set in the current save flow.
5. **V2 spec not persisted:** Saving after V2 generation does not store the spec; detail page cannot show V2 content. Any “canonical V2” or print-from-V2 after save would require persisting the spec (e.g. in evaluacion_generada) and loading it on the detail page.
6. **Two PDF implementations:** EvaluationRendererV2 (html2canvas + jsPDF) and EvaluationContentWrapper (html2pdf.js); behavior and styling may differ.
7. **Detail page has no V2 and no PDF:** EvaluacionDetalle only uses EvaluacionVisualRenderer (HTML); it does not use EvaluationContentWrapper or EvaluationRendererV2, and has no PDF export in the paths reviewed.
8. **Normalizer is the single place** that converts `equivalentResponseOptions` (object or array) to `responseOptions`; all UI reads normalized shape.

## 8. Ready-to-Plan Changes

- **Equivalent options in question layout:** Plan changes to EvalItem/ResponseOptions (or a new inline variant) so options can be rendered inside the question block (e.g. below prompt, same card), and optionally a prop/flag to choose “inline” vs “box” without changing backend contract.
- **Remove “Ítems” column from map:** Plan removal or hiding of the second column in MapTable.tsx (and adjust header/totals row if needed).
- **Rubric per question:** Plan extension of V2 spec (e.g. `item.rubric` or section-level rubric array) and either Edge Function prompt/output or frontend derivation; plan persistence and UI to display/edit per-item rubric.
- **Print/PDF from single source:** Plan unifying PDF export (one implementation and one set of print styles) and, if desired, making the detail page print/PDF-friendly (e.g. use EvaluationContentWrapper or add PDF button and optional V2 load from persisted spec).
- **Persist V2 spec:** Plan storing `evaluationSpec` (or equivalent) in `evaluacion_generada` when saving after V2 generation, and loading it on EvaluacionDetalle to optionally render with EvaluationRendererV2 and preserve PDF/print from V2 content.
